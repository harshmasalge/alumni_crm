# M1.1 — People Segmentation, Groups & Permission-Aware Export

**Status:** Phases A–C complete 2026-09-20 (verified below); Phase D final validation in progress.
**Parent:** M1 complete, accepted by owner 2026-09-18 ([M1.md](M1.md)).

## Phase A — People Segmentation: complete

### What was built

- **Filter model/DSL:** `FilterGroup {op: and|or, conditions}` of
  `FilterCondition {field, operator, value/values}` (16 fields across
  Company/Role/Personal; per-kind operator whitelists; depth ≤ 3, ≤ 50
  leaves). `groups` remains contract-reserved and rejected with a clear
  400 — filtering *by group membership* was never in M1.1 scope (groups
  are managed populations, not a search field).
- **Server-side engine** (`apps/api/src/app/services/segmentation.py`):
  validated tree → correlated EXISTS SQL over affiliation/education/address
  history; tenures derived from `start_date` at query time (never stored).
- **API:** `POST /api/v1/constituents/search` (filter tree + M1 criteria
  `q`/`roll_no`/`organisation_q`/`stale_threshold_days` as one intersection;
  server-side pagination, `display_name`/`year_of_graduation` sorting),
  `GET /constituents/search/fields` (registry for the UI),
  `/api/v1/taxonomies` (CRUD + deactivation + usage counts + 409 referential
  protection), `GET/PATCH /api/v1/organisations/{id}` (company_type/HQ master
  data). M1 GET search, stale, org search, 360°, and append flows untouched.
- **Data model** (migration `f3a91c4d55e2`): `people.last_name`,
  `affiliations.function`/`seniority_level`, `organisations.company_type`/
  `hq_city`/`hq_state`/`hq_country`, `taxonomies` table seeded with 44
  observed industries + 5 company types. Excel profiled first (4,101 rows);
  function/seniority intentionally unseeded (no structured source).
- **Profile 360:** career table shows Function/Seniority; add-job form writes
  them; identity edit/display covers last name. Decisions in
  [ADR-005](../decisions/ADR-005-segmentation-taxonomy.md).
- **People UI (extends M1 screen, refined 2026-09-19):** workspace layout —
  segmented People/Organisation tabs with explicit active state; search
  controls incl. stale filter; results (~70%) + collapsible filter sidebar
  (~30%, full width when collapsed) with collapsible COMPANY/ROLE/PERSONAL
  sections, per-filter accordions, per-section active counts, multi-value
  tags with taxonomy suggestions, nested-logic editor, and a Groups/Phase-B
  unavailability note. Action toolbar above results shows the population
  count ("N alumni" vs "N alumni match these filters"), removable active-
  filter chips, clear-all (structured filters only), and the Filters toggle;
  the toolbar's right slot now hosts the Phase B Add-to-group and Phase C
  Export actions (no placeholder buttons were ever used). Server-side pagination,
  loading/empty/error states, stale + org + name + Roll Number combination
  preserved. Master Data lives under Administration → Master data (visible
  to `constituents.write` holders without `admin.*`; user/role admin stays
  admin-gated). Existing M1 search, results, 360°, and navigation preserved.
- **Authorization:** existing named dependencies only
  (`check_constituents_read`/`check_constituents_write`); no new permissions
  in Phase A. Field-level `FieldPermissionChecker` behavior unchanged and
  applied to advanced results (proven: viewer sees no `notes`, staff does).
- **Audit:** middleware covers `SEARCH_FILTERED`, `FILTER_FIELDS`,
  `TAXONOMY_LIST/WRITE`, `ORG_READ/WRITE`; taxonomy/org writes add explicit
  `log_audit` rows with before/after (metadata only, never row data).

## Phase B — Groups & Governance

### B1 — Backend foundation: complete (2026-09-19, no UI)

- **Tables** (migration `b1a91c4d77e2`): `groups` (unique name, no hard
  delete), `group_memberships` (current-state + `UNIQUE(group,
  constituent)`), `group_rule_versions` (append-only JSON snapshots;
  partial unique indexes: one ACTIVE + one PENDING per group),
  `group_membership_proposals` (version-bound, reason snapshots,
  proposer/evaluator/approver identities, applied_at).
- **APIs** (`/api/v1/groups`): CRUD + deactivate/reactivate; manual
  member add/remove (idempotent `{added, already_members, invalid}`);
  `preview` (dry-run, exactly one of ids/filter) and `materialize`
  (re-evaluated filtered add); rule propose/list/approve/reject/evaluate
  (ACTIVE only); proposal list/approve/reject with stale-version 409s.
- **Governance:** rule approval (approver ≠ proposer) activates the version
  and auto-evaluates into PENDING proposals only; membership approval
  (approver ≠ evaluator) applies rows; self-approval 403 everywhere, no
  bypass; reasons snapshotted per leaf (expected vs actual).
- **Permissions:** `groups.read/create/update/manage_members/manage_rules/
  approve/deactivate` via existing seed + migration grants (admin 7, staff
  7, viewer read-only). Seven named dependency gates; field-level
  `FieldPermissionChecker` on member lists; centralized audit
  (`GROUP_*` actions + middleware coverage).
- **Verification:** `tests/test_groups_b1.py` **7 passed** (auth matrix,
  lifecycle/idempotency, field security, two-stage + self-approval + stale
  versions, preview/materialize/reject paths, combined-population parity,
  audit); full suite green with the unrelated photo test deselected.
  Decisions: ADR-006.

### Phase C — Permission-Aware Export: complete (2026-09-20)

- **APIs** (`/api/v1/exports`, no schema change besides the permission
  row in migration `c1a91c4d88e2`): `GET people/fields` catalog (per
  column allowed/required-permission flags); `POST people` returning
  `.xlsx` (bold headers, frozen panes, sane widths, Content-Disposition
  filename). The column registry derives from the 360° response models
  (singletons flat, lists as counts + joined columns), so new profile
  fields become exportable automatically under existing permission
  checks; Aadhaar/ciphertext/files/photos/audit excluded by rule.
  Populations: explicit IDs (validated), M1 + filter tree
  re-evaluated, or group members (`groups.read` additionally enforced).
  5000-row single-request cap (422 with guidance); zero-result exports
  return headers-only workbooks.
- **Security:** `constituents.export` gate (admin + staff; viewer/finance
  403 even for reads of the catalog); requested columns intersected with
  field permissions (drop/mask semantics identical to profile reads);
  unknown columns 422; direct-bypass, ghost-ID, and unknown-group cases
  tested; audit `EXPORT_PEOPLE` carries population/column/count metadata
  only. Deliberately no `groups.export` permission: group export rides
  the same endpoint + `groups.read`, so no second export permission was
  needed.
- **UI:** shared Export dialog on the People toolbar (ids / filtered /
  all populations) and Group member lists; permission-aware column
  picker with disallowed columns explained, never hidden; blob download.
- **Verification:** `tests/test_exports_c1.py` **4 passed** (allow-list
  unit + gates/catalog/population-parity/group/audit integration with
  real XLSX parsing); full suite **51 passed** (photo test deselected);
  `npm run check:crm` green (29 modules). Decisions: ADR-007.

#### Final requirement audit (M1.1 prompt §§2–33)

Implemented: all 16 segmentation filters with per-kind operators; generic
reusable filter DSL; nested AND/OR evaluated server-side; result counts +
server-side pagination/sorting; M1 search combination (intersection);
data-model extensions without flattening; Profile 360 career/last-name
coverage; staff-managed taxonomies (44 industries + 5 company types seeded
from real data; function/seniority staff-populated); Manual + rule-based
groups; pending-proposal workflow with per-leaf reasons; rule-version
governance (pending → approve → auto-evaluate → membership approve);
no-silent-change guarantees (403 self-approval, 409 stale versions);
group permissions via existing RBAC (+ migration grants); field-level
security on People, groups, and exports; filtered/unfiltered Excel export
with permission-aware columns and re-evaluated populations; sync-first
XLSX (worker-compatible contract); centralized audit throughout (metadata
only); phase-gated delivery with stops.
Partial (documented, by design): position tenure ≈ company tenure;
org-master UI is API-only; resolved-org matching is M3 scope; evaluation
cost is per-leaf EXISTS (fine at current scale); proposal counts page
through the UI loop past 100.
Not implemented (out of M1.1 scope, future milestones): saved searches;
async export jobs/scheduling; finance-module exports; alumni portal;
M2–M7 scope. Unrelated pre-existing photo-test issue untouched throughout.
